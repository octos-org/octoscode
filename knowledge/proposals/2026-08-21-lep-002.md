# Global 运行时生命周期:外环发起、共驾与交还

## Context

LEP-001(accepted)覆盖了对**已运行**内环的观测(REQ-OLP-OBS)与控制
(REQ-OLP-CTRL 的 steer),但运行时**生命周期本身**仍由 operator 手动
承担:开一个终端跑 octoscode TUI。三个实测约束决定了这不可省略也不可
简单绕过:(1) session 是 client-connection-coupled——server 与模型都
不能开会话,`peer/staged` 必须由 client 消费,**没有 client 的 serve
peer 永远起不来**(M15 契约);(2) serve 对 per-cwd instance 持排他锁,
同工作区只能一个实例(实测锁竞争 = "启动黑屏"事故);(3) TUI 需要真
tty(splash/渲染/审批键)。因此 F1 无人值守长跑的前置问题是:**外环
如何发起一个合法的 client+serve 运行时,保持人类可随时旁观与接管**。

## Motivation

"octoscode 作为 CC/Codex 的 agent runtime" 的完整故事要求外环一条命令
拉起内环。今天的桥方案(tmux 共驾)已完成技术验证设计但未执行:真 tty、
`send-keys` 注入、`capture-pane` 给外环"眼睛"、operator `attach` 共驾。
需要在流程上定下:桥的纪律边界,以及终态形态。

## Goals

- 外环可编程地:启动 global 实例、检测存活、注入指令、感知画面状态、
  异常时重启、任务结束后交还/关停。
- operator 随时可旁观(attach)与接管,审批权始终在人(R3 红线)。
- 与 serve 锁语义、client-coupled 契约完全兼容——不绕过、不放宽。

## Non-Goals

- 放宽 M15 "server 不自开会话" 契约(headless **client** 是 client,
  不是服务端开会话)。
- 外环代 operator 按审批(无论 send-keys 还是未来 API)。
- 多实例并发同一 cwd(锁语义不变;多项目并行 = 多 cwd 多实例,天然支持)。

## Decision

两阶段:

**阶段 1 — 驾驶舱共驾桥(零上游改动,即刻可用)**

- 载体(operator 2026-08-22 拍板):**脚本化进 repo**
  (`scripts/octos-global.sh` + runbook),把注入纪律与前置检查做成
  机制而非自觉。
- **驾驶舱后端抽象**:脚本封装统一的 launch/inject/read/attach 四原语,
  后端两实现——**herdr 优先**(Omarchy 生态,agent 级原语:
  `herdr agent prompt`/`agent read`/`agent send-keys`,免键盘模拟时序
  竞态)、**tmux 回退**(`send-keys`/`capture-pane`,无 herdr 环境通用)。
  session 名 `octos-global`,`-c <repo>` 锚定 cwd。
- **注入纪律(外环 MUST)**:每次 `send-keys` 前先 `capture-pane -p`
  判定画面状态;检测到 approval/question 卡时 MUST NOT 注入任何按键,
  改为通知 operator(衔接 REQ-OLP-CTRL-NOTIFY);注入内容仅限 composer
  文本 + Enter 与 Esc 级导航,MUST NOT 注入 y/s/n 等审批键。
- **启动前置检查(MUST)**:检测同 instance 的 serve 锁持有者;有则拒绝
  启动并报告(绝不 kill 抢锁——那是 operator 决定)。
- **存活与重启**:外环以既有 Monitor(serve 日志 + git HEAD)判活;
  tmux session 消失或 serve 锁释放且非计划关停时,通知 operator 后方可
  重启(不静默自愈,避免掩盖崩溃)。

**阶段 2 — headless client 终态(octoscode 侧改动)**

- octoscode 增加无渲染 client 模式(形态待拍板:`--headless` 标志或
  独立薄二进制):承担 client 的全部协议职责——capabilities 握手、
  session/open、消费 `peer/staged` 打开 peer 会话、事件泵——但不渲染、
  不读键盘;指令入口只走 REQ-OLP-CTRL 的 steer,观测只走 REQ-OLP-OBS。
- TUI 降级为可选的"attach 视图"(与 headless client 互斥持锁,或经
  未来共享后端连接)。阶段 2 落地后 tmux 桥退役为调试手段。

## Compatibility

- serve 锁、client-coupled、peer depth-1 等契约原样保留。
- 阶段 1 纯外部工具(tmux),对两仓库零代码改动;阶段 2 是 octoscode
  新增模式,不改既有 TUI 行为。
- 与 REQ-OLP-CTRL(steer)/REQ-OLP-OBS(观测)是拼图关系:阶段 2 的
  headless client 假定两者已落地,故实施排序在 M3 之后。

## Migration Plan

N/A -- no migration required(阶段 1 无状态;阶段 2 为新增模式)。

## Security Considerations

- `send-keys` 等价于完整键盘权限 == operator 权限,这是桥的最大风险面:
  靠注入纪律(不碰审批键 + capture 前置检查)约束,并在 runbook 中声明
  该纪律不可由模型自行豁免。阶段 2 从结构上消除此面——headless client
  不暴露键盘,审批 API 不进外环可用面。
- tmux session 属同 UID;不引入网络面。

## Privacy Considerations

capture-pane 内容可能含会话文本,仅用于外环本地判定,不外发、不落盘
(除非 debug 显式保存)。

## Risks and Assumptions

### Assumptions

- tmux 在目标环境可用且 operator 熟悉 attach/detach。Invalidated if:
  部署环境无 tmux——届时阶段 2 提前。
- capture-pane 足以可靠判定 approval 画面(有边框与固定标题)。
  Invalidated if: 主题/布局改版使判定不稳——加机器可读状态行或提前
  依赖 REQ-OLP-OBS 事件流判定。

### Risks

- 桥期外环误注入(时序竞态:capture 与 send 之间弹出 approval)。
  Mitigation:send 后立即再 capture 复核;approval 到达本身有账本
  escalation 事件可交叉验证。
- 常驻实例长期运行的 serve 内存/日志增长。Mitigation:runbook 纳入
  定期计划内重启(goal ledger 使任务跨重启存活,实测 boot reconcile
  有效)。

## Consequences

Good:F1 无人值守长跑的最后一个人工环节(开终端)被移除;operator
获得"随时 attach 的驾驶舱"而非黑盒;阶段 1 零开发成本即可开始积累
运行数据。

Bad:桥期的安全边界靠纪律而非机制;tmux 成为部署依赖(至阶段 2 为止)。

## Alternatives Considered

- **python pty 驱动**(已做过技术验证):无人类可视界面,operator 无法
  旁观接管——弃。
- **systemd 用户服务只跑 `octos serve`**:没有 client,peer 会话永远
  打不开,违背 client-coupled 契约的现实——弃。
- **放宽 serve 允许服务端自开会话**:违背 M15 编排契约,影响面不可控
  ——弃。
