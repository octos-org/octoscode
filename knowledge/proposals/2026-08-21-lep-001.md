# octoscode/octos 作为外部强模型的 Agent Runtime(OLP v1)

## Context

过去 48 小时的双环实验(外环 Claude Code / Fable 5,内环 octos master +
peers / moonshot k3)已把 goal_01–04 四轮长程任务跑通,并沉淀了
`docs/OUTER_LOOP_PROTOCOL.md`(OLP v0)与 `AGENTS.md` 协议注入。实测证明
指导环(AGENTS.md 金丝雀、黑板 ACK、打回→整改→**后续行为改变**)、执行环
(handoff/ledger/escalation/wake)、审计环(双路监控、R2 复验、R4 纪律)
均已闭合。但同批实验也暴露了系统性缺口:外环靠翻目录+自算不稳定 hash+
grep 人类日志观测;idle master 需要 operator 说一句话才能被唤起;peer
shell 无工具链导致"未验证"交付;验证声明靠自觉曾两次失实;多写者仅靠
纪律兜底。

## Motivation

让 octoscode + octos 成为 Claude Code / Codex 的**执行运行时**:强模型只做
计划/监控/审查/指导,苦力模型承担全部执行迭代。实测 token 经济学:一轮
goal 收尾内环跑 12+ 轮迭代,外环仅 4 次事件驱动介入——强模型消耗与任务
时长解耦。这是 octoscode 的差异化能力("王炸"),现在补齐接口即可产品化。

## Goals

- 外环零 TUI 交互即可:发现状态(观测面)、下达带确认的指导(控制面)、
  信任交付(机制化验证)。
- 无人值守长程:goal + budget 下 keeper 驱动多轮 handoff→审查→整改,
  operator 仅出现在目标设定与终审。
- 模型分层开箱可用:苦力车道(sub_providers)有模板、有选道说明、可审计。

## Non-Goals

- 外环代 operator 批审批(OLP R3 红线)。
- 将 goal 文本注入 peer 微观 context(违背宏观 goal 设计)。
- 第二个 stdio client 并存(serve 排他锁语义不变)。

## Decision

分三个里程碑补齐六组缺口(编号沿用外环审查记录):

**M1 观测(全部小改,先行)**
- A1 只读状态 CLI:`octos goal status --json`、`octos peer list --json`、
  `octos ledger tail <goal_id> --json`;纯读 redb/文件,不依赖 serve 存活。
- A3 稳定寻址:`octos inbox path --session <key>` 查询命令(现 DefaultHasher
  跨版本不稳定,上游注释自认);或改 SHA-256 截断 + 一次性迁移。
- D1 苦力车道模板:`sub_providers` 样例配置(cheap/strong + description
  写选道标准,description 进 handoff 工具 schema 使 master 自主选道)。
- E1 result.md schema 固化:frontmatter 增加 `verified:` 与
  `protocol: olp/v1`;黑板 ACK 语法定式 `ACK(done|wontdo|blocked): <说明>`,
  `wontdo` 即分歧路径——外环只能接受或升级 operator,不得循环打回。
- E3 可执行合约:`specs/task-agent-runtime-olp.spec`,场景绑定 A1–C3 的
  集成测试。

**M2 硬化**
- A2 结构化事件流:serve 追加写 `<data_dir>/events.jsonl`
  (`{ts, kind, goal_id?, slug?, session?, model_lane?, detail}`),kind 覆盖
  `peer_staged/finding_recorded/escalation/goal_transition/steer_consumed/
  turn_error`;同时修复日志按进程启动日期滚动的观测坑。
- C1 工具链继承:peer/master 工具 shell 继承 operator PATH 或 profile
  `tool_path`(实测 peer 无 cargo 只能交付"未验证")。
- C2 隔离默认化:`peer_handoff.worktree` 缺省 profile 可配,实施类 brief
  建议默认 true(现仅靠 AGENTS.md 纪律防多写者互踩)。
- C3 机制化验证(R2 落地为代码):profile 配置 `verify_command`;peer
  交付时 runtime 执行并把 `verified: pass|fail|skipped(原因)` 写入
  result.md frontmatter 与 ledger(实测内环两次以 lib-only 绿色失实声称)。
- D2 车道可观测:peer_staged 事件带 `model_lane`,外环审计成本分布。

**M3 控制面与自治**
- B1 带 ACK 的 steer:`octos steer --session <key> --text <指令>`——持久
  排队、注入下一 turn、events.jsonl 出现 `steer_consumed` 即机器可读 ACK;
  复用 `enqueue_goal_progress_wake` 的唤醒机制,消除"门铃 + operator 说
  一句话"。
- B2 `.reviewer-notes` sidecar(持久直至显式确认);B1 落地后降级为别名。
- F1 无人值守长跑验收(见 Consequences 的验收场景)。
- F2 升级通知:R3 第三级接外部通知(复用 octos cron notify mode),避免
  escalation 无人值守时静默 park。

## Compatibility

- CLI 与公共 API:A1/A3/B1 为**新增**子命令,不改既有语义;serve 排他锁、
  peer 深度 cap、brief 64KB 等治理约束原样保留。
- 文件格式:result.md frontmatter 增量字段(旧消费者忽略未知键);
  events.jsonl 为新文件;inbox 哈希若迁移需一次性重命名脚本。
- 既有 specs/KLL:`specs/task-startup-splash.spec` 等不受影响;本提案
  接受后按 `## Produces` 铸 REQ,后续 task spec 以 `satisfies` 关联。

## Migration Plan

仅 A3 若选择更换哈希需迁移:提供 `octos inbox migrate`,按旧算法枚举
现存 `.notes/.lock` 并重命名;其余均为增量,`N/A`。

## Security Considerations

- B1 是新的指令注入面:限 localhost/unix-socket、与 serve 同 UID;steer
  内容作为**数据**注入 prompt(与 peer brief 同级信任,非系统指令)。
- C3 的 `verify_command` 是任意命令执行:只允许来自 operator 手写的
  profile 配置文件,禁止模型/黑板/steer 写入或修改该字段。
- events.jsonl 只含已写入日志同级的元数据,不新增敏感面。

## Privacy Considerations

events.jsonl 与 --json 输出均落在既有 per-instance data dir(0700 语义
沿用 peers/ 的 0600 惯例);不新增遥测,不外发。

## Risks and Assumptions

### Assumptions

- 内环模型(k3 级)在 AGENTS.md + 黑板约束下能持续遵守 ACK/纪律。
  Invalidated if: 换更弱模型后 ACK 率显著下降——届时需 C3 式机制替代
  更多纪律条款。
- goal keeper 的 continuation 机制足以承载 steer 唤醒。Invalidated if:
  B1 实测发现 idle(无 goal)session 无法被 continuation 唤起,需补
  session-level 唤醒。

### Risks

- steer 滥用导致内环上下文污染。Mitigation:steer 带 `[external-reviewer]`
  来源标记,单 turn 注入量有 cap(复用 notes 的 64KiB 读取上限)。
- verify_command 拖慢 peer 吞吐。Mitigation:profile 可按 brief 类型
  跳过(分析类 skip),结果如实标 `skipped`。

## Consequences

Good:外环接入面收敛为"四件套 + 两条 CLI",任何强模型可标准化接入;
R2 从纪律变机制;长程任务的强模型成本近似 O(审查次数) 而非 O(迭代次数)。

Bad:octos 新增两个对外表面(steer、events)需要长期维护;verify_command
把项目构建时间引入 peer 关键路径。

验收(端到端,即 F1):外环在零 TUI 交互下——A1/A2 发现状态 → B1 下达
指导 → 内环执行并以 E1 语法 ACK → 外环复验 C3 机器验证结果并打回一次 →
内环整改 → goal complete;operator 仅执行初始 `/goal` 与终审;期间任一
escalation 触发 F2 通知。

## Alternatives Considered

- **外环直连 LLM API 编排(LangChain 式)**:放弃,octos 已有 durable
  goal/ledger/escalation,重造运行循环违背 M15"编排不进客户端"契约。
- **外环做第二个 stdio client**:放弃,serve 排他锁与 redb 单写者语义
  冲突,实测锁竞争即"启动黑屏"事故源。
- **把指导全部塞进 goal objective 文本**:放弃,实验已证 CC 式每 turn
  注入的 goal 文本不被稳定 honor,宏观/微观分离是本架构的立身之本。
